01 / AGENT 技术解析

让 Agent 放手跑测试之前，先把沙箱边界画清楚

明天又整什么 · 2026-10-25 · UTC+8

独立阅读与分享本篇 ↗

让 Agent 自己跑测试，和把整台电脑交给它，中间应该有一道真正的门。

你让一个编码 Agent 修复导出功能。它读代码、改文件，接着想运行测试。你点了一次允许。测试又拉起脚本，脚本再启动另一个进程——这时，你批准的究竟是一行命令，还是它接下来能碰到的一切？

今天只拆一个机制：编码 Agent 的 Shell 沙箱。以 Claude Code 为例，重点不是模型会不会听话，而是即使它走错路，执行环境还允许它走多远。这是已有工程机制的选读，不是今日新功能发布。

把“别碰”从提示词变成执行边界

提示词里的“不要修改项目外文件”是一条行为要求。沙箱则在操作系统层限制进程访问资源：哪些路径可写，哪些位置不可读，网络能连到哪里。模型可以提出动作，但不能仅靠提出动作就获得资源。

Anthropic 2025 年的原文介绍，运行时在 Linux 使用 bubblewrap、在 macOS 使用 Seatbelt，限制也覆盖命令启动的子进程。2026 年的后续文章把这件事概括为控制潜在损害范围。两篇文章讨论的是防线设计，不是“沙箱永远无法被突破”的承诺。

仍然用“修导出”这个任务走一遍

假设项目在 /work/exporter。一个可审查的任务配置是：代码目录可写，依赖缓存按需要开放；私人文件与凭据目录拒绝读取；默认不出网，需要安装依赖时再明确允许目标服务。这里是编辑设计示例，不是可直接复制的产品配置。

这样，测试可以生成报告、创建临时文件。即使某个测试脚本启动子进程，它也仍在同一执行边界里。若脚本试图读私人目录或连接未批准地址，应由边界拒绝，而不是等模型自觉停下来。

失败信息也很重要。一次“连接被拒绝”，可能表示依赖确实缺失，也可能表示脚本正在做任务之外的事。先看它要访问什么，再判断是否应当开放。把整个网络放开，只是把问题藏回去了。

为什么文件和网络要一起管

只限制写文件，仍可能把可读内容发出去；只限制网络，又可能让进程改写以后会执行的配置。两道边界共同缩小风险，但每一项允许都仍有含义：能向某个代码托管域名发请求，不等于只能访问你自己的仓库。

当前官方文档还特别说明，内置代理默认不检查加密连接里的内容。“域名在名单上”不是“请求内容已经安全审核”。因此，不应把敏感数据直接放进可读范围，再寄希望于一个宽泛的域名名单替你兜底。

最容易漏掉的是沙箱外的工具

按本次核验的 Claude Code 滚动文档，Shell 沙箱覆盖 Shell 命令及其子进程；文件工具、MCP 服务与 hooks 不在这一沙箱里。若另一个连接器能改线上数据，Shell 再严格，也没有限制那条路径。工具权限需要独立检查。

同样，沙箱不能判断业务结果对不对。在允许写入的项目内删错文件，仍可能完全符合资源边界。代码差异审查、测试和发布权限，解决的是不同层次的问题。

上线前，验证“拦得住”也验证“做得完”

可以在不含真实秘密的测试工作区做一次边界验收：正常导出测试应完成；子进程读取一个专门放在禁止路径下的无害样本应失败；访问一个未批准的测试地址也应失败。然后检查拒绝记录，确认不是“任务失败后悄悄在沙箱外重跑”。这些是建议的验收步骤，本刊未做产品安全实测。

取舍就在这里：收紧边界会增加依赖配置与兼容性维护，放宽边界又会扩大一次误操作的影响。适合从一个边界清楚的修复任务开始，让 Agent 在里面充分行动，再根据真实需要扩大范围。自主执行的前提，是先知道自主发生在哪里。

02 / 后端技术解析

翻到第 500 页为什么变慢？把 OFFSET 换成游标之前

明天又整什么 · 2026-10-25 · UTC+8

独立阅读与分享本篇 ↗

用户只是再往下滑一屏，数据库为什么要从头数到第十万行？

订单后台最初只有几百条记录。接口写成 LIMIT 20 OFFSET 0，简单好用。后来业务变大，翻到深处越来越慢；有人刚翻完第一页，第二页竟又见到同一笔订单。

这两个现象可以用同一个主题解释：分页到底记住的是位置，还是边界？今天用 PostgreSQL 18 的语义拆解游标分页，也叫 keyset pagination。它不是某个新版本刚推出的魔法功能，而是一种查询设计。

先把“第几页”换成“从哪一条继续”

OFFSET 说的是：先跳过这么多行，再取结果。PostgreSQL 文档明确提醒，被跳过的行仍须在服务端计算，所以大偏移量可能低效。即使有索引，“跳过十万条”也不等于免费移动到一个数组下标。

还有一个更直观的问题。按创建时间倒序看订单，第一页显示 A、B、C。此时新订单 X 插到最前面，第二次请求再跳过三条，列表变成 X、A、B、C……你就又拿到了 C。这是位置变化导致的重复，不是数据库忘了去重。

一个时间戳还不够

游标记住上一页最后一条记录的排序键。下一页问“在它之后的记录有哪些”，不再问“排在第六十一位的是谁”。不过，只按 created_at 排序不够：同一时刻可能有多笔订单，必须加一个唯一的决胜字段。

下面约定 id 是唯一主键，created_at 非空且创建后不改；租户由服务端鉴权上下文决定。每页显示 20 条，但查询 21 条，用额外一条判断是否还有下一页：

SELECT id, created_at, total_cents
FROM orders
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 21;

$2、$3 是上一页最后一条实际展示的记录，不是多查出来的第 21 条。第一页省略游标条件。倒序对应小于号；同一时间下再比较 ID，才不会把同一秒里的其余订单一起跳掉。

PostgreSQL 的行值比较从左往右找到第一个决定结果的字段。这正好对应上面的排序。不要把升序、降序混搭后仍照抄这个条件，也不要忽略空值：参与比较的空值可能让判断成为 unknown。本文通过非空约束避开这个分支。

索引要和这个问题一起设计

CREATE INDEX orders_tenant_feed_idx
ON orders (tenant_id, created_at DESC, id DESC);

等值过滤的租户放前面，后面跟排序键。这给数据库提供了按租户定位、沿排序边界继续读的路径；不是承诺任何数据分布下都会选择它。新增状态过滤、复杂关联或者很宽的返回列，都可能改变计划与成本。

真正验收时，拿代表性的首屏与深页查询查看 EXPLAIN (ANALYZE, BUFFERS)，关注实际读行、排序与缓冲区访问。该命令会执行查询，应先在合适的测试数据上使用。这里给的是检查方法，没有虚构“快了多少倍”。

游标不是权限，也不是快照

实现接口时，我会让游标携带时间、ID、筛选条件摘要和格式版本，并做完整性校验。它只是续读提示；服务端每次仍要重新验证租户与访问权限。把 JSON 做成 Base64，并不会让它变得不可篡改。

更重要的是，游标只能减少“前面新增记录导致后面位次平移”的影响。若排序键会变，一条记录仍可能跨过边界而重复或漏读；已删除的记录也不会凭空回来。所以订单流适合不可变的创建时间，频繁修改的更新时间流要另想清楚语义。

财务导出若要求“某一刻的完整集合”，不能靠跨多次普通 HTTP 请求携带游标来保证。应该另行定义一致快照或离线导出任务。游标解决续读，不负责冻结世界。

那“直接跳到第 500 页”呢？

这恰好是它不擅长的地方：没有前一页边界，就无法直接接着读。无限滚动、按时间查看订单很合适；随机跳页、精确总页数，可能仍值得保留偏移分页或单独维护导航信息。

因此，别把一次查询改写当成所有分页需求的统一答案。先确定用户是要“继续看”，还是要“按页码定位”。当需求确实是继续看时，记住上一条，比反复从头数更贴近问题本身。

03 / 科技动态

AI 用量终于补进报表，一张太空自拍也值得重看

明天又整什么 · 2026-10-25 · UTC+8

独立阅读与分享本篇 ↗

一边是终于补进报表的 AI 使用量，一边是一张十二年前的太空自拍。今天值得看的，是数字与画面背后容易漏掉的那一层。

这份周日动态只留两件事：一项直接影响开发团队观察工具使用情况的更新，以及一张被重新选中的航天照片。第一件是本周新公告，第二件是新推荐里的旧影像，时间先说清楚。

AI 工具换了入口，统计也得跟上

如果团队有人在 IDE 里用 Copilot，有人在 OpenCode 等工具中把 Copilot 当模型服务，过去看编辑器统计，可能看不全后者的用量。

GitHub 10 月 23 日的公告补上了这个缺口：Copilot usage metrics API 新增 totals_by_client，在企业、组织及相应用户级的 1 天、28 天报告中按客户端展示请求与 token 等用量。官方举例包括 OpenCode；这不是“OpenCode 的所有活动都被 GitHub 收集”，范围是经由 Copilot 的模型流量。

有两个小字比大标题更值得读。request_count 数的是成功的模型调用，不是一条用户提示；一个提示可能触发多次调用。客户端分类又来自请求携带的集成标识，是尽力归类，不能当作经过验证的身份。

所以，报表里某个入口突然变多，先别急着解释成“大家产出翻倍”。也可能是过去没进统计的流量，现在终于进来了。用量、产出与质量，是三个不同的问题。

我的阅读结论是：这项更新更适合拿来讨论团队要支持哪些入口，以及旧报表漏看了什么。看一个工具是否有价值，仍要结合任务完成、代码审查和返工；不能用 token 数给工程师排座次。这是编辑分析，并非 GitHub 的效果承诺。

访问也有门槛：需要相应角色或查看指标权限，并开启 Copilot usage metrics 策略。官方 API 文档说明报告按日生成；它不是实时监控屏。公告描述的是 API 增量变化，没有给出一个需要安装的客户端版本号。

这张“自拍”，拍摄者其实还没离开母船

NASA 的 10 月 24 日每日天文图选中了 Rosetta 的一张自拍。别被当天日期误导：照片拍于 2014 年 10 月 7 日，ESA 在同月 14 日发布。那时它距离彗星 67P 表面约 16 公里。

前景是探测器的一侧和一片 14 米长的太阳翼，背景则是那颗形状特别的彗星。掌镜的不是远处另一艘飞船，而是仍搭载在 Rosetta 上的 Philae 着陆器的 CIVA 相机。

画面还有一个很“摄影”的细节：亮处和暗处差异太大，于是团队合并了两张不同曝光时间的照片，才把两边的细节一起呈现出来。ESA 原始说明与 NASA 本次介绍都提到了这一点。它是处理过的科学影像，不应被描述成手机随手拍的一次曝光。

我喜欢它的原因并不玄：太空任务常以轨道和参数出现，而这张照片让机器自己的边缘也进入画面。太阳翼不再只是规格表上的一个长度，成了观看彗星的前景。原始影像的吸引力，已经足够，不需要再给它补一个虚构的故事。

从工具报表到航天照片，今天这两条都有个值得保留的阅读习惯：看见结果时，多问一句“它怎样被记录下来”。你会少误读一些数字，也多看见一点细节。
