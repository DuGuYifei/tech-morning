ISSUE 015 / 03 / 科技动态

AI 用量终于补进报表，一张太空自拍也值得重看

GitHub 补齐 Copilot 客户端用量统计；NASA 重新推荐 Rosetta 自拍。看清统计口径，也看清照片的真实时间。

明天又整什么 · 2026.10.25 · UTC+8

一边是终于补进报表的 AI 使用量，一边是一张十二年前的太空自拍。今天值得看的，是数字与画面背后容易漏掉的那一层。

这份周日动态只留两件事：一项直接影响开发团队观察工具使用情况的更新，以及一张被重新选中的航天照片。第一件是本周新公告，第二件是新推荐里的旧影像，时间先说清楚。

AI 工具换了入口，统计也得跟上

如果团队有人在 IDE 里用 Copilot，有人在 OpenCode 等工具中把 Copilot 当模型服务，过去看编辑器统计，可能看不全后者的用量。

GitHub 10 月 23 日的公告补上了这个缺口：Copilot usage metrics API 新增 totals_by_client，在企业、组织及相应用户级的 1 天、28 天报告中按客户端展示请求与 token 等用量。官方举例包括 OpenCode；这不是“OpenCode 的所有活动都被 GitHub 收集”，范围是经由 Copilot 的模型流量。

有两个小字比大标题更值得读。request_count 数的是成功的模型调用，不是一条用户提示；一个提示可能触发多次调用。客户端分类又来自请求携带的集成标识，是尽力归类，不能当作经过验证的身份。

所以，报表里某个入口突然变多，先别急着解释成“大家产出翻倍”。也可能是过去没进统计的流量，现在终于进来了。用量、产出与质量，是三个不同的问题。

我的阅读结论是：这项更新更适合拿来讨论团队要支持哪些入口，以及旧报表漏看了什么。看一个工具是否有价值，仍要结合任务完成、代码审查和返工；不能用 token 数给工程师排座次。这是编辑分析，并非 GitHub 的效果承诺。

访问也有门槛：需要相应角色或查看指标权限，并开启 Copilot usage metrics 策略。官方 API 文档说明报告按日生成；它不是实时监控屏。公告描述的是 API 增量变化，没有给出一个需要安装的客户端版本号。

这张“自拍”，拍摄者其实还没离开母船

NASA 的 10 月 24 日每日天文图选中了 Rosetta 的一张自拍。别被当天日期误导：照片拍于 2014 年 10 月 7 日，ESA 在同月 14 日发布。那时它距离彗星 67P 表面约 16 公里。

前景是探测器的一侧和一片 14 米长的太阳翼，背景则是那颗形状特别的彗星。掌镜的不是远处另一艘飞船，而是仍搭载在 Rosetta 上的 Philae 着陆器的 CIVA 相机。

画面还有一个很“摄影”的细节：亮处和暗处差异太大，于是团队合并了两张不同曝光时间的照片，才把两边的细节一起呈现出来。ESA 原始说明与 NASA 本次介绍都提到了这一点。它是处理过的科学影像，不应被描述成手机随手拍的一次曝光。

我喜欢它的原因并不玄：太空任务常以轨道和参数出现，而这张照片让机器自己的边缘也进入画面。太阳翼不再只是规格表上的一个长度，成了观看彗星的前景。原始影像的吸引力，已经足够，不需要再给它补一个虚构的故事。

从工具报表到航天照片，今天这两条都有个值得保留的阅读习惯：看见结果时，多问一句“它怎样被记录下来”。你会少误读一些数字，也多看见一点细节。
