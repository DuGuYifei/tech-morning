翻到第 500 页为什么变慢？把 OFFSET 换成游标之前

从订单列表的慢查询和重复记录出发，拆解 PostgreSQL 游标分页的排序键、索引、实现与一致性边界。

明天又整什么 · 2026.10.25 · UTC+8

用户只是再往下滑一屏，数据库为什么要从头数到第十万行？

订单后台最初只有几百条记录。接口写成 LIMIT 20 OFFSET 0，简单好用。后来业务变大，翻到深处越来越慢；有人刚翻完第一页，第二页竟又见到同一笔订单。

这两个现象可以用同一个主题解释：分页到底记住的是位置，还是边界？今天用 PostgreSQL 18 的语义拆解游标分页，也叫 keyset pagination。它不是某个新版本刚推出的魔法功能，而是一种查询设计。

先把“第几页”换成“从哪一条继续”

OFFSET 说的是：先跳过这么多行，再取结果。PostgreSQL 文档明确提醒，被跳过的行仍须在服务端计算，所以大偏移量可能低效。即使有索引，“跳过十万条”也不等于免费移动到一个数组下标。

还有一个更直观的问题。按创建时间倒序看订单，第一页显示 A、B、C。此时新订单 X 插到最前面，第二次请求再跳过三条，列表变成 X、A、B、C……你就又拿到了 C。这是位置变化导致的重复，不是数据库忘了去重。

一个时间戳还不够

游标记住上一页最后一条记录的排序键。下一页问“在它之后的记录有哪些”，不再问“排在第六十一位的是谁”。不过，只按 created_at 排序不够：同一时刻可能有多笔订单，必须加一个唯一的决胜字段。

下面约定 id 是唯一主键，created_at 非空且创建后不改；租户由服务端鉴权上下文决定。每页显示 20 条，但查询 21 条，用额外一条判断是否还有下一页：

SELECT id, created_at, total_cents
FROM orders
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 21;

$2、$3 是上一页最后一条实际展示的记录，不是多查出来的第 21 条。第一页省略游标条件。倒序对应小于号；同一时间下再比较 ID，才不会把同一秒里的其余订单一起跳掉。

PostgreSQL 的行值比较从左往右找到第一个决定结果的字段。这正好对应上面的排序。不要把升序、降序混搭后仍照抄这个条件，也不要忽略空值：参与比较的空值可能让判断成为 unknown。本文通过非空约束避开这个分支。

索引要和这个问题一起设计

CREATE INDEX orders_tenant_feed_idx
ON orders (tenant_id, created_at DESC, id DESC);

等值过滤的租户放前面，后面跟排序键。这给数据库提供了按租户定位、沿排序边界继续读的路径；不是承诺任何数据分布下都会选择它。新增状态过滤、复杂关联或者很宽的返回列，都可能改变计划与成本。

真正验收时，拿代表性的首屏与深页查询查看 EXPLAIN (ANALYZE, BUFFERS)，关注实际读行、排序与缓冲区访问。该命令会执行查询，应先在合适的测试数据上使用。这里给的是检查方法，没有虚构“快了多少倍”。

游标不是权限，也不是快照

实现接口时，我会让游标携带时间、ID、筛选条件摘要和格式版本，并做完整性校验。它只是续读提示；服务端每次仍要重新验证租户与访问权限。把 JSON 做成 Base64，并不会让它变得不可篡改。

更重要的是，游标只能减少“前面新增记录导致后面位次平移”的影响。若排序键会变，一条记录仍可能跨过边界而重复或漏读；已删除的记录也不会凭空回来。所以订单流适合不可变的创建时间，频繁修改的更新时间流要另想清楚语义。

财务导出若要求“某一刻的完整集合”，不能靠跨多次普通 HTTP 请求携带游标来保证。应该另行定义一致快照或离线导出任务。游标解决续读，不负责冻结世界。

那“直接跳到第 500 页”呢？

这恰好是它不擅长的地方：没有前一页边界，就无法直接接着读。无限滚动、按时间查看订单很合适；随机跳页、精确总页数，可能仍值得保留偏移分页或单独维护导航信息。

因此，别把一次查询改写当成所有分页需求的统一答案。先确定用户是要“继续看”，还是要“按页码定位”。当需求确实是继续看时，记住上一条，比反复从头数更贴近问题本身。
