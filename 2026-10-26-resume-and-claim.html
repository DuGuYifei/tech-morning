01 / AGENT · 文档选读

点了“继续”，
哪段会重跑？

Agent 等待人确认时，保存状态只是起点。用 LangGraph 的 interrupt 看一遍恢复路径。

可访问性短摘要与实施边界

恢复使用原 thread_id 和 Command(resume=...)；发生中断的节点会从开头重跑。把确认前的写操作改为幂等，或拆到确认后的独立节点。生产存档需持久化；内存存档不跨进程重启。稳定操作键应绑定业务对象及版本，执行前重新检查权限和已批准版本，外部结果不明时查询原操作。代价是存档、状态迁移和去重协议的维护；没有外部去重能力时，不能承诺恰好执行一次。

来源与版本：LangGraph Python · Interrupts；Persistence。滚动文档未单列发布日期，本刊核验于 2026-10-26；讲解当前文档语义，不声明某个未测试安装版本。图2、3中的发送流程为编辑设计。

02 / BACKEND · 机制选读

别让所有 worker
等同一行。

几台机器同时生成缩略图，先解决“谁拿走哪份任务”，再解决“谁失败了怎么办”。

领取 SQL 与可访问性短摘要

编辑示例：jobs.id 为主键，status 为任务状态；:token 是本次领取的新唯一令牌。事务结束后再做图片处理。租约长度需按业务耗时选择，长任务需续租；以下 5 分钟仅为示意。

BEGIN;
WITH picked AS (
 SELECT id FROM jobs
 WHERE status = 'ready'
 ORDER BY id
 LIMIT 1 FOR UPDATE SKIP LOCKED
)
UPDATE jobs AS j
SET status = 'running', claim_token = :token,
    lease_until = now() + interval '5 minutes'
FROM picked
WHERE j.id = picked.id
RETURNING j.id, j.claim_token;
COMMIT;

处理完成时，用 id、status='running' 和当前 claim_token 做条件更新；更新零行表示本次领取已失效。回收器也须有竞争控制，不能无条件覆盖新的领取。ready 任务可考虑按 id 建部分索引并用真实分布检查执行计划。

SKIP LOCKED 跳过抢不到行锁的任务，能减少队头等待，但不保证公平和严格 FIFO。锁在事务结束时释放，租约、失败回收、重试上限和外部幂等需要应用补齐。适合已有数据库、队列规模可控的任务；高吞吐、复杂路由或严格顺序需求要评估专门队列。示例未作性能测试。

来源与版本：PostgreSQL 18 · SELECT / Locking Clause；13.3 Explicit Locking。官方持续维护手册，页面未单列原发日期；核验 2026-10-26。租约与领取令牌是本文应用层设计，不是数据库内置保证。
